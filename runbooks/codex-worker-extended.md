# Codex worker extended rules

These rules moved from AGENTS-codex.md to keep the always-loaded file short.
Read the relevant section when a task uses Hub planning or a Spec Tree project.

## Hub workflows and file locations

Hub's `development` skill covers debugging, tests, review and verification. Its
`hub-planning` skill handles substantial team work. Small, clear tasks need neither a
planning document nor an extra approval round. When planning files are needed:

- **Specs** → `~/hub/projects/<repo>/YYYY-MM-DD-<topic>-design.md`, committed in `~/hub`.
- **Plans** → `~/hub/projects/<repo>/YYYY-MM-DD-<feature>-plan.md`, committed in `~/hub`.
- **Worktrees** → reuse the workspace `hub claim` prints; `.worktrees/` is ignored per clone by
  `hub init-repo`. Never add it to a shared `.gitignore`.
- **Executing a plan with several agents**: the plan's tasks become `hub` tasks (the
  `hub-planning` skill says how). Work one session does alone follows its steps directly.

## Spec projects: build from the PRD

Some projects have a PRD under `~/hub/projects/<p>/spec/` (the Spec Tree, `HUB.md` "Spec Tree"). Their tasks
are generated by `hub spec apply`; `hub show` prints the acceptance lines a task implements as `reqs`. There:

- **Cite every line you implement, at its current version**, as `Req: A-3.2@2` lines plus `Task: T-n`, in the
  PR body or a commit message. The current versions are in the task and its issue. A missing or stale `Req:`
  holds the PR with a comment; nothing reviews or merges it until a new commit carries the right lines.
  On a `task/T-n` branch `hub live` adds any missing `Closes #`, `Req:` and `Task:` lines to the PR body itself.
- **Your PR body needs an `## Evidence` block (or `Verified:` line) and a `Not verified:` line**, in your own
  words. `hub done` refuses until the open PR has both.
- **Never touch `spec/` or `tests/acceptance/`.** Those are Zeus's. The one exception: a check-writer task
  assigned to you ("land acceptance checks") is where you write `tests/acceptance/`. A PR that touches either is held for Zeus
  and never merged by `hub live`. If an acceptance test looks wrong, `hub block` and tell Zeus.
- **A clearly wrong PRD line: fix small errors, propose big ones; never work around it.** A duplicate or
  contradiction the lint flags, or wording that leaves every line's meaning and test unchanged, is corrected
  with `hub spec correct <file>` (Hermes reviews it). Anything that changes what gets built is reported with
  `hub spec propose <file>` and your evidence, for the lead. Until T-577 adds both commands, `hub block` and tell Zeus.
- **Never read `~/hub/projects/*/heldout/`.** Those are held-out checks; a PR that carries one is held. A red
  held-out check names only its line: re-read that line's text and edge cases, and never ask for the check.
- **Build on the change branch the brief names** (`change/C-NNN`): `hub claim` already puts your workspace at
  `origin/change/C-NNN`. Branch there and open the PR against it, not `main`. Do not reuse an old clone of
  that branch.
- **Never `hub new` or `hub edit` a task's brief or verify there** (refused). If the task is wrong, block it.
- **If you are told your task is superseded, stop.** Abandon its branch and run `hub next`; the replacement is
  a new task.
