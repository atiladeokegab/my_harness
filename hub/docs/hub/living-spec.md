# Living Spec (the Spec Tree)

Part of the hub manual. Index: `$HUB_DIR/HUB.md` (default `~/hub/HUB.md`).

## Living Spec: the PRD drives the board (`hub spec`, `hub prd`)

A project with `projects/<p>/spec/prd.json` (or legacy `requirements.json`) is a **spec project**. The PRD is
its only source of truth: every change of intent is an approved delta that increments the PRD version, and
`hub spec apply` regenerates the task tree from it. Nobody writes or edits those tasks by hand. A worked
example lives in `tests/fixtures/spec_linkly/`.

| File in `projects/<p>/spec/` | Holds |
|---|---|
| `prd.json` (or `requirements.json`) | The PRD: header, constraints (`stack`, `non_goals`, `limits`), requirements with `why`, `needs` and declared `touches`, each with numbered acceptance lines (`A-3.2`) at a version naming its test under `tests/acceptance/` |
| `changes/C-NNN.json` | One change (proposal or correction): `base_version`, `based_on_version`, `based_on_sha256`, `modified`, `added`, `removed`, `author`, `by`, `note` or `reason` |
| `spec.lock` | The spec version, sha256 of the spec file, and the commits each applied change rewound |
| `reviews/` | Review approval receipts (`<cid>-review.json`) recording `approved_path` and `approved_sha256` |
| `review-C-NNN.html` | Self-contained one-tap review page generated by `hub spec propose` for human approval |
| `projects/<p>/heldout/` | Private held-out checks run by the change gate; hidden from builders |

```bash
# PRD inspection, rendering and authoring
hub prd show <p>                               # display the PRD as Markdown
hub prd render <p> [--out FILE]                # render the self-contained HTML page
hub prd check <p>                              # validate schema, structure and rules
hub prd grill <p> [--answer FIELD=VALUE]       # interactive interview to close gaps and refine fields

# Spec lifecycle and graph operations
hub spec init <p> [--from seed.json]           # first PRD: v1 and spec.lock (the lead, at spec approval)
hub spec check [--project <p>] [--repo DIR]    # schema, lock hash, acceptance tests both ways
hub spec lint C-NNN [--project <p>]            # deterministic overlap checks (L1–L9, L12–L16) for a change
hub spec impact C-NNN [--project <p>]          # the blast radius, from the graph alone
hub spec rewind C-NNN --dry-run [--project <p>]# rewind and every acceptance check, in a throwaway clone
hub spec apply C-NNN [--project <p>] [--force] # PRD v+1, branch change/C-NNN, the regenerated tree
hub spec correct <file> [--project <p>]        # propose a bounded correction (small typo/clarity, 0 blast radius)
hub spec propose <file> [--project <p>]        # propose a spec change and generate review-C-NNN.html
hub spec revert C-NNN [--project <p>]          # restore previous version by creating a reversing correction
hub spec approve C-NNN [--why "..."] [--project <p>] # reviewer approves a change file, recording a receipt
hub spec bootstrap-sha T-5=<sha> --project <p> # one-time: merge_sha for tasks merged before it was recorded
hub spec converge [--project <p>]              # weekly (hub-weekly.service): one task per drift from the live line

# Provenance and governance
hub trace <target> [--project <p>]             # provenance for A-n.m[@v], R-n, T-n, sha, #N, PR#N
hub agents                                     # each agent's autonomy phase, budget, and live capabilities
hub agent phase <name> <phase> --why "..."     # promote or demote an agent's autonomy phase (lead only)
```

`--repo` defaults to `$HUB_CODE_DIR/<p>`.

**The Living Spec components.**

1. **Deterministic linting (`hub spec lint`).** Implements rules L1–L9 and L12–L16: duplicate text (L1),
   method/path conflicts (L2), shared test path (L3), return shape conflicts (L4), near-duplicate text (L5),
   shared requirement title head (L6), shared file references (L7), overlapping pending changes (L8),
   missing held-out checks (L9), dependency cycles in needs (L12), overlapping touches across requirements (L13),
   length budgets (L14), requirement ranking (L15), and missing test paths (L16).
2. **Provenance with `hub trace`.** `hub trace` inspects the entire chain of custody across PRD lines,
   requirements, tasks, PRs, git commits, and review receipts. Example: `hub trace A-1.1`, `hub trace T-42`,
   or `hub trace 8f50d37`.
3. **Held-out checks and canary.** In addition to visible tests in `tests/acceptance/`, spec projects
   maintain private held-out checks in `projects/<p>/heldout/` that builders never see. When a change
   branch's tasks finish, the change gate runs visible tests, then held-out checks. If a held-out check
   fails, the gate reports the line ID alone (`held-out A-8.1`), never the check code or test logic. A canary
   in each held-out file catches a held-out file's text appearing in a PR diff.
4. **Stack table and undeclared dependencies.** Each spec project maintains a stack table (the PRD's
   `constraints.stack`, else `docs/stack.md`) with Decided and Proposed rows. When a PR adds a dependency or
   tool (in `pyproject.toml`, `package.json`, Dockerfile, etc.) not on a Decided row, `hub live` holds the PR
   until the stack change is reviewed and approved.
5. **Autonomy: fix small errors, propose big ones.**
   - **Corrections (`hub spec correct <file>`):** When an agent spots a typo, wording ambiguity, or lint
     duplicate/contradiction that leaves acceptance criteria and task validity intact, it submits a correction.
     The tool verifies: blast radius is 0, modified fields are strictly `text` or `test`, the change keeps
     similarity at 0.80 or more and changes 80 characters or fewer, `"previous"` is taken from the spec,
     `"author"` is recorded, and self-approval is forbidden. Approved with a review receipt by an agent in the
     `reviewer` or `lead` phase.
   - **Proposals (`hub spec propose <file>`):** For changes to requirements, new features, or anything with
     non-zero blast radius. Generates a standalone review page (`review-C-NNN.html`); requires a lead approval
     receipt.
   - **Reverts (`hub spec revert C-NNN`):** Generates a reversing correction restoring the previous text/test.
   - **Receipt gate.** For `hub spec apply`, the receipt is the gate, not the actor. Any non-`off` agent
     can run `hub spec apply` once the required receipt exists (lead receipt for proposals, reviewer/lead
     receipt for corrections).
6. **Autonomy phases and governance (`hub agents`).** Agent capabilities are defined in `factory.json` across
   five phases: `off`, `trial`, `trusted`, `reviewer`, and `lead`. Run `hub agents` to inspect current agent
   phases, per-task budgets, and active permissions (`fast_lane`, `done_force`, `review`, `hand_merge`).
   Trial builders never take fast-lane merges (all PRs wait for the configured reviewer). Promotions and
   demotions are governed by `hub agent phase <name> <phase> --why "..."`.

**A change, step by step.**

1. You state new intent and the lead agent writes a proposal, or an agent writes a correction
   (`hub spec correct <file>`) or proposal (`hub spec propose <file>`). No code or task moves.
2. `impact`, then `rewind --dry-run`: the done tasks citing a changed line, the later commits entangled with
   them, and any kept check that goes red once they are reverted (a hidden dependency, which joins the rebuild).
   Same inputs, same report: no LLM in it.
3. A check-writer (a sub-agent of the lead, never a builder of a line it checks) writes the tests for added and
   changed lines and runs only lint on them. Its task is done when each check lands, is collected and fails only
   for the missing behaviour (an expected red, shown by running it independently); the full `make check` runs
   later, at the green gate. Its verify collects them (`collect_cmd` in the `factory.json` repo entry, default
   `uv run pytest -q --collect-only {test}`). The build tasks keep the green gate.
4. The reviewer or lead approves the change file (`hub spec approve` or via the review HTML page), generating a
   receipt in `reviews/`. A proposal needs your approval, in a `hub review` window or the review page.
5. `apply` refuses without a matching receipt, with a stale lock, while an earlier change has not landed, or if
   `change/C-NNN` exists. A radius over half the done tasks needs `--force`. Then it pushes `change/C-NNN` (the
   rewind commit) to origin, writes PRD v+1 and the lock, and regenerates the tree: done tasks outside the radius
   carry over, re-pinned to the new version; done tasks inside are rewound and rebuilt; every unfinished task is
   tagged `stale` and replaced. A line the change leaves untouched that no task covers (built before its check
   landed) is listed as "no checks yet", never turned into a build task. A builder holding a stale task is told to
   stop and abandon its branch.
6. Rebuild tasks cite `reqs` (`A-3.1@2`), list the rewound files, and build on `change/C-NNN`. Their PRs target it.
7. `hub live` merges task PRs into the change branch. When its tasks are done and no PR into it is open, a
   detached gate runs every current acceptance check, the smoke, `make check`, and held-out checks on its head
   (`change_timeout` in `factory.json`, default 1800 s). Green, the branch joins `integration` as one unit, then
   smoke, promote, deploy, like any merge.

**Generated tasks verify** with their own lines' acceptance checks, then
`hub spec check --project <p> --repo . --lines <its A-ids>`: schema, lock and links in full, but a missing test file
only for the task's own lines, so a sibling's unbuilt check never blocks it. Not `make check`: the full suite stays
the integration gate's job. Plain `hub spec check` still reports every missing test file.

**Weekly converge.** Every Monday `hub spec converge` clones each spec project's live line and runs `check`,
every acceptance check whose test exists, and held-out checks. A check red 3 times out of 3 is drift, red some
of the time is reported as flaky, and every check red at once is one environment task, not one per line. It opens
one task per drift for the lead agent, deduplicated by title, and never edits the spec. Paused hub: it opens nothing.

**Trailers.** Every PR in a spec project carries `Req: A-3.2@2` (each line it implements, at its current
version) and `Task: T-n`, in the body or a commit message. `hub live` comments on and holds a PR with no `Req:`
or a stale version, and never reviews or merges it. `Req: ci-fix` passes only on a PR that `Closes #` its ci-fix
task's own issue. The squash keeps the trailers and `hub live` records `merge_sha` on the task.
A PR from `task/T-n` that lacks `Closes #`, `Req:` or `Task:` gets them from the board once, put at the top of its
body by `hub live`. Evidence stays the builder's: `hub done` on a factory task refuses while its open PR has no
`## Evidence` block (or `Verified:` line) or no `Not verified:` line, and only warns when gh is unreachable.

**Approval is a receipt, nothing else.** A review page with `data-approves=<path>` makes `hub review` record the
file's path and the sha256 of the bytes you approved. `apply` accepts only a receipt whose hash equals the
change file now; an edit after approval voids it. A hash written into the change file itself proves nothing.

| Who | May | May not |
|---|---|---|
| You | Approve proposals in `hub review` or review pages; promote/demote agents (`hub agent phase`) | |
| Agent in lead phase (`$HUB_LEAD`) | Write PRD and proposals, `init`, apply changes with receipt, clear `stale`, merge PRs touching `spec/` or `tests/acceptance/` | Self-approve own proposals |
| Agent in reviewer phase (`$HUB_REVIEWER`) | Review PRs; approve PRD corrections (`hub spec approve`); request changes on board (`hub changes`) | Approve own corrections; merge PRs touching protected paths |
| Builders (trial/trusted) | Build generated tasks on `change/C-NNN`, citing current `Req:` lines; submit corrections (`hub spec correct`) and proposals (`hub spec propose`); run `hub spec apply` with valid receipt | Touch `spec/` or `tests/acceptance/` (held for the lead); `hub new` in a spec project, edit a generated task's brief or verify, claim a `stale` task (all refused); read `projects/*/heldout/`; self-approve corrections; bypass review if in `trial` phase |
| Check-writer (the lead's sub-agent) | Write `tests/acceptance/` on the change branch | Build the feature it tests |
